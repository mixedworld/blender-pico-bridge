# QR pairing, curved monitor measurement and viewport linking

Experimental feature branch: `feature/qr-monitor-viewport-sync`. Build the add-on **0.4.0** and APK together from this branch. The published 0.3.0 downloads do not contain these features. This is a draft implementation, not a verified automatic monitor alignment release.

## Pair from Blender

Open the **PICO Bridge** sidebar. **Start when panel opens** starts the local server once; disable it for manual startup. New installations default to Visible Scene. Existing collection/selection settings are retained. The server can pair before valid geometry is selected; choose a source and Refresh Model to publish geometry.

The panel shows the server IPv4 address, manual token entry/copy and an on-screen QR. **Show QR and markers** adds a larger QR and four corner OpenCV `DICT_4X4_50` markers plus a central reference (ID 4, when there is sufficient room) to the selected 3D Viewport. The overlay is display-only and does not add geometry to the scene. Markers are sized for camera visibility and inset around overlapping Blender headers, toolbars, sidebars and shelves so their complete white borders stay visible. The transmitted marker rectangles retain full-viewport pixel coordinates. Stop Bridge removes its QR preview/temp file. Do not share screenshots containing a real pairing QR: it contains the bearer credential.

In the PICO app, open **Connection**. It requests camera permission and starts looking for the Blender QR. Valid bridge QR data automatically fills the pairing details and connects; other QR codes are ignored. Only literal private/loopback IPv4 HTTP endpoints and our versioned QR scheme are accepted. The initial connection also checks the QR's server session; restarting the bridge requires a fresh scan. Manual connection remains available, including for hosts that need a different route.

Choose **Connect via → Wi-Fi / LAN** when the headset can reach the computer's advertised address. A QR cannot configure a firewall or connect isolated networks. If the Mac and headset are on different networks, use **USB / Emulator (ADB)** and run `adb -s DEVICE reverse tcp:8766 tcp:8766` for that device (replace DEVICE with its `adb devices` serial). This mode deliberately advertises `http://127.0.0.1:8766` through the USB tunnel. The displayed URL, copied details and QR all use the selected route; changing the route updates the QR without restarting the server. Changing the server port requires a matching reverse mapping.

**Show large pairing QR** toggles the QR independently from the markers, even when a headset is already connected. Its size follows the viewport so it remains readable on a high-resolution monitor. If scanning stalls, the status distinguishes service startup, first-frame acquisition and live QR searching.

## Move and recover the toolbox

The toolbox is an independent PICO OS window in both Preview and Room. Pinch its system movement handle to reposition it. Its native close button closes only the toolbox; press the compact **Tools** button beside the model to reopen it. This action expands the menu and reuses the same tagged window when it is already open. Connection, alignment and inspection values remain in the application-scoped state. Placement after a closed window is recreated is managed by PICO OS.

The user verified native movement and close/reopen recovery in Room on the real headset. Preview uses the same tagged window with a recovery button attached to the Preview volume; interactive Preview recovery still needs verification.

## Manual alignment with five handles

**This is the primary alignment method.** In **Room → Align viewport** (**Align monitor** in older builds), four cyan handles appear at the frame corners and an amber handle appears at the top centre.

**Place the handles on the Blender 3D viewport image boundary, not the physical monitor corners.** Exclude the bezel, Blender headers, Timeline, Outliner and other panels. This is the rectangle whose camera image is synchronized; using the whole monitor changes the projection window and can offset or mis-scale the model. Maximize the viewport first if you want it to cover most of the display, then keep that layout unchanged.

1. Pinch each cyan handle and place its **centre** on the corresponding viewport corner: top-left, top-right, bottom-right, bottom-left. Each moves independently in 3D; moving one does not move the other three. The visible cubes are 14 mm with 36 mm pick targets.
2. Pinch the amber top-centre handle and move it in/out until it touches the middle of the viewport's top edge. It stays on the top midpoint's depth axis. A flat screen uses the flat stop; a concave screen moves the middle behind the left/right corner chord. Its lateral/upward motion is ignored so this step changes curve without skewing the frame.
3. The live outline stays attached to the four corner cubes and amber top-centre handle on every drag, including temporary nonrectangular placements. It is an editable bowed guide through those points. When the corners are crossed, twisted or too far from a rectangle, correct the points until the message clears; the rectangular/cylindrical calibration is accepted only when valid. **Lock alignment** and **Stage for take** are disabled for an invalid draft. The fit supports a horizontal cylindrical curve of 0–120°, with surface arc width and height 0.1–2 m.
4. Choose **Stage for take**, then **Lock alignment**. The handles disappear and their input components are removed. The fitted cylindrical occlusion mask activates; the hidden model remains grabbable through it. The user verified model grabbing after Stage/Lock and movable corners after reopening alignment on the real PICO. Reopening alignment turns viewport linking off and restores the Blender source view while editing.

To adjust an already staged/locked setup, reopen **Align viewport**. Each edit session creates fresh handle input targets and restarts the gesture recognizer. The model's grab proxy is suspended while alignment is being edited, including pose/bounds updates, then rebuilt when you lock or leave editing. You can repeat Stage → Lock → Align without restarting the app. The SDK resources retained across removal/recreation use explicit ownership (`toGlobal()` with matching disposal); without this, the SDK freed the physics/mesh resources at lock and reopening failed. Two native tests passed on the real PICO: ten production handle lock/reopen cycles and ten collision-resource removal/replacement cycles. The user also confirmed the corrected build supports both model grabbing after staging/locking and independent corner movement after reopening alignment.

The width/height sliders remain as alternatives and rebuild the handle positions from the current fit. **Reset corner handles** also rebuilds them from the last valid surface; it discards an invalid draft. QR/marker and touch flows remain available and hide manual handles while capturing.

The depth mask is disabled during manual handle editing so it cannot hide or visually separate the guides. A staged model can remain visible until you lock the frame. Locking applies the validated cylindrical surface, rather than the temporary bowed outline.

The five-point fit assumes a rectangular viewport on a horizontally cylindrical screen. It is not an arbitrary quadrilateral warp or a measurement of an irregular screen surface. Raw handles remain at your placements while editing; the outline passes through them, even before a rectangular fit is possible. Curved monitor projection in Blender still uses the chord approximation described below. The user confirmed all five handles are visible and the corners move independently on the real PICO. Numerical fit and application-state tests pass; the user also confirmed that the repaired outline stays attached throughout uneven corner and curve adjustments. Physical calibration accuracy remains unverified.


## Retain the frame after restarting (real PICO)

**Lock alignment** now also saves the viewport calibration to a persistent PICO world anchor on the headset. Allow **Spatial data** if requested. The toolbox confirms **Viewport frame and curvature saved** when both the anchor and device-local calibration have been stored. The exact four corner positions, amber handle's curvature/sagitta, physical width/height and frame orientation are retained. For matching model content, the staged fit is saved too.

1. Align the five handles to the **Blender 3D viewport boundary**, choose **Stage for take → Lock alignment**, and wait for the save confirmation.
2. After restarting the app, reconnect if necessary and enter **Room**. Look towards the same viewport and around the nearby room so PICO can recognize the saved location.
3. The frame restores automatically once the saved anchor is located. The same scene restores its saved staged fit; different content is fitted behind the retained frame. Enable **Link Blender viewport** when ready.
4. To change the alignment, choose **Align viewport**, move the handles and lock again. The old saved anchor is replaced only after the new anchor and calibration are successfully stored.

A room anchor remembers a physical location; it does not follow a monitor that has been moved. Realign after moving/resizing the viewport or moving the display. If PICO cannot locate the anchor, the app leaves the saved calibration intact and offers the existing manual alignment path instead of applying coordinates from an old session. Curvature is not re-estimated on restore. Clearing application data, uninstalling, or deleting PICO's room/anchor data can remove the saved alignment. Live relocalization requires a real headset; emulator build/tests cannot prove it.

Implementation/build and coordinate round-trip tests pass. The user confirmed saving the frame and curvature on the real PICO. After a full process stop/relaunch, device logs confirmed localization of the saved UUID and restoration of all four corners and the same 23.34° curvature, with no fresh crash-buffer entries. The user then confirmed on the real headset, without realigning, that the frame, curve and staged model still match Blender’s viewport after restart.

## Alternative: known marker size and horizontal curve

Use **Room → Align viewport → Scan known-size marker** when screen depth is unreliable. This path uses camera intrinsics and the physical marker size, without sensor depth.

1. Hide the large pairing QR, leaving the markers visible. Measure the outer **black** square of one displayed marker in millimetres, excluding its white margin. Set **Marker black edge · mm**. A new installation starts at 50 mm **unconfirmed** and cannot scan until you set a measured value. The confirmed measurement is saved locally. Re-measure after changing Blender's display scaling, marker pixel size, viewport or monitor.
2. Set **Total horizontal curve · degrees** (0° is flat). This is the total cylindrical sweep across the selected Blender viewport, not the monitor's advertised radius. For a known radius, sweep in radians is surface arc width divided by radius. The profile illustrates the angle. Blender's **Center reference only** overlay mode can isolate the single measured marker; **Show all markers** restores the corner references. This mode does not verify curvature.
3. Tap **Scan**. The camera preview shows solid detected marker outlines and dashed fitted projections. At least one marker can establish scale and pose for an assumed curve; several widely separated markers, especially the centre plus corners, are needed to check that curve against the image. With at least three markers, a bounded angle search can suggest a lower-error curve in the status; it never changes your chosen angle. Adjust either slider during scanning; changing a value invalidates the previous candidate and starts a fresh stability window.
4. Keep the markers steady. A candidate needs at least eight consistent estimates, no more than 3 px RMS reprojection error, and a plausible camera-space distance (0.15–5 m). Higher-error fits remain visible for adjustment but cannot be accepted. **Pause for review** freezes the image and estimate.
5. In Room, the scan now also calibrates the camera-to-head transform from multiple stationary head views. Keep at least three separated markers visible, turn left/right and tilt up/down, and pause around two seconds at each angle. At least 12 distinct views with rotation about more than one axis are required. A fresh-camera-data check and a one-second head-stability window reject moving or stale samples. The head buffer uses local receipt times; this is not an exposure-timestamp synchronization claim.
6. **Pause for review** becomes available after the world calibration passes. Review the dimensions and status, then choose **Use alignment**. The scene owner converts the measured global position and rotation into the existing monitor parent's coordinates and locks the monitor automatically. Locking hides its guide frame; reopen **Align viewport** to inspect the frame at the calibrated pose without dragging, then lock it again. No dragging of the monitor plane is required. Cancel, backgrounding, a resized board or a changed measurement invalidates the candidate and preserves the previously applied calibration. This integrated world-alignment path is installed for physical testing; a real scan passed its calibration checks with 15 distinct held views (6.6 mm position RMS and 0.54° rotation RMS on held-out observations). Visual placement is awaiting the headset check.

A good image fit does **not** prove physical scale: an incorrect marker measurement can produce the same projection at an incorrect distance. One marker also cannot independently identify screen curvature. Keep Blender's viewport dimensions unchanged during scanning and review; a changed board layout invalidates the candidate. Rectified camera frames and outlines stay in app memory and are cleared when the flow ends; they are not saved or sent to Blender.

Once the monitor is locked, its occlusion strips have no collision or interaction components: gaze/pinch can reach the model's existing grab collider through the visually opaque mask. Reopening alignment restores plane picking; lock the frame before pulling the hidden model. The user confirmed grabbing the fully hidden model through the locked plane on the real PICO.

The curved proxy is a horizontal cylinder approximation with 32 adjoining occlusion strips and matching guides. Width means **surface arc length**, height is vertical, and 0° retains one flat strip. Staging puts the model behind the full surface; source hiding waits until the model clears its maximum depth. This geometry is unit tested, but real-device curved occlusion and the physical measurement workflow still require interactive validation.

The world-alignment implementation uses public HMD tracking and metric ArUco poses to measure a rigid camera/head calibration: `globalFromHead × headFromCamera × cameraFromMarker = globalFromMonitor`. OpenCV hand–eye calibration estimates `headFromCamera`; it is not assumed to be the rendering camera or derived from IPD. Every fourth view is excluded from the fit and used to check world-pose consistency. Acceptance requires position RMS ≤12 mm, angle RMS ≤1.2°, bounded maximum residuals, a plausible camera/head offset and nonparallel rotational motion. These numerical thresholds are provisional pending physical validation. The existing Full Space scene consumes the validated global pose through public Entity conversion APIs. This avoids relying on the unavailable SpatialML-scene-to-ECS handle bridge.

Camera/head calibration is currently repeated for each scan and is not saved. The existing preview-volume workflow is unchanged; automatic world alignment requires Room/Full Space. It does not infer marker size or curvature without the confirmed measurement/settings.

## Device-local camera diagnostics

The normal app uses the intrinsics returned with each camera capture. A measured profile can be installed by an explicit opt-in instrumentation diagnostic; it is not a universal focal correction or an automatic calibration feature. The profile is private to the application and scoped to the exact firmware fingerprint, image dimensions, eye and originating SDK matrix. It is accepted only with sufficient samples, low reprojection residual and bounded focal uncertainty. Other installations and changed firmware/capture geometry retain the SDK matrix. Camera images are never written by these diagnostics.

The opt-in `PhysicalMarkerProbeTest` requires `physical_camera=true` and explicit board/measurement arguments. Without that argument it skips. Its camera test needs at least four detected markers; a timeout is a failed/inconclusive physical test, not an accepted alignment. The optional numerical residual sweeps are disabled in the normal app.

For native capability discovery, install the debug and androidTest APKs, then run `python3 tools/probe_openxr.py --device SERIAL --ndk /absolute/path/to/android-ndk` with ADB on PATH. The helper builds a small JNI library locally, initializes the public Khronos Android loader, enumerates extensions, then removes the helper from app storage. It creates no OpenXR instance/session and captures no images. An Android NDK is required only for this optional probe, not the application build.

`MarkerAnchorRenderProbeTest` is a separate opt-in visual diagnostic. It uses the already paired GLB and validated local camera profile, follows stable board poses through SpatialML's documented camera anchor, then locks for 25 seconds before releasing its scene. It requires explicit `side_mm`, `curve_deg` and `model_scale` arguments, affects no Blender object or saved monitor pose, and does not provide an ECS world-transform bridge. The real-device test completed its Follow and Locked submissions without an API exception. Visual world-lock accuracy remains unconfirmed. Successful submission alone does not establish correct visual placement or exposure-time compensation. The normal bridge does not activate this diagnostic.

On the tested headset, public OpenXR enumeration succeeded and returned 86 extensions, but did not advertise `XR_BD_camera_image`, `XR_PICO_camera_image` or `XR_EXT_spatial_image_tracking`. This rules out relying on those advertised public paths in this build; it does not establish that privileged or other platform SDK camera paths are absent. The public `XR_BD_camera_image` contract describes per-image camera intrinsics/extrinsics and capture-time VIEW-to-local registration, but is not available through this tested enumeration.

## Alternative: measure the viewport with depth

Use **Room → Align viewport → Measure with markers + depth**, grant Camera and Spatial Data, and look at the four markers. The implementation:

1. Acquires 1280×960 rectified stereo, timestamp and intrinsics in one SpatialML capture. The supplied matrix reports nearly identical horizontal/vertical focal lengths at this 4:3 size. The known-size investigation below found a mismatch between that matrix and the delivered image geometry on the tested firmware; equal reported focal lengths do not prove square sampling. QR decoding was verified at 4:3; it failed with the earlier 16:9 request.
2. Reads RGB into app memory, detects four markers with OpenCV and samples a 5×5 interior grid per marker (100 depth points).
3. Keeps that capture frozen while `uvTo3DInCameraSpace` projects those image points using its depth/stereo registration. Per-marker depth clustering and median positions reduce isolated bad samples.
4. Rejects nonfinite, zero/out-of-range, nonrectangular, noncoplanar or ambiguous results. A temporal innovation gate rejects size jumps before scalar Kalman filtering; at least 12 accepted estimates with deviations within 1.5 cm are required.
5. Extrapolates from the marker-center insets to the full viewport rectangle. **Use measured size** applies only width/height to the existing monitor plane, leaving it unlocked for manual placement/confirmation.

No physical width is requested or guessed. Camera frames are not written to disk or uploaded to Blender. Cancelling, leaving the scan surface or backgrounding the app stops acquisition. A timeout or denied permission preserves manual setup.

**Depth-only world placement remains incomplete.** Use the known-size hand–eye path above for the new world-registration flow. The public 6.1.9 projection API documents camera-space XYZ. Current HMD poses are available, but the public API does not establish the VST exposure-camera extrinsic or expose historical timestamped HMD poses. SpatialML's `CameraAnchor.Locked` world-locks its own scene, with no verified handle-to-existing-ECS-plane bridge here. Applying a current HMD pose as if it were calibrated exposure data is deliberately not implemented.

A bounded real-device projection diagnostic confirmed the current XY pixel convention: its camera-intrinsic reprojection residual was about 3–4 pixels, versus about 300 pixels with swapped axes. On the tested screen, individual markers still reported incompatible depths (roughly 0.8 m on the right versus 2.8–4.8 m on the left), and the filtered fit correctly remained unstable. Depth freshness, metric accuracy on other surfaces and world registration remain unverified. The temporary diagnostic has been removed from the normal app. Flat-screen size estimates do not reconstruct a curved display: four corner samples cannot measure its center curvature or radius. Reflective/curved displays can produce inaccurate or missing depth. Do not treat this path as curved-screen calibration.

## Align by touching marker centers

When screen depth is unreliable, use **Room → Align viewport → Touch marker centers**. Keep Blender's four markers visible and its window/layout unchanged during capture.

1. Choose the index finger that will touch the screen (right by default), then **Start touching**.
2. Rest that fingertip on the marker center in the order **top-left → top-right → bottom-right → bottom-left**. Keep both hands in view.
3. When the status says **Ready**, pinch with the opposite hand to record the point. Release that pinch before recording the next marker. The touching hand stays extended against the screen.
4. Review the measured dimensions, choose **Use alignment**, inspect the plane, then **Lock alignment**. Cancel/restart preserves the previous calibration until you explicitly accept the new result.

The app samples the public hand provider's global index-tip position in metres, requires at least eight samples spanning 200 ms with positions within 8 mm of their median, and records only on a fresh opposite-hand pinch. The confirming pinch is calculated from tracked thumb/index distance (20 mm closed, 45 mm open, with separate press/release thresholds). This avoids depending on the OS pinch `isReady` flag, which stayed false on the tested headset despite both hands being tracked. Multiple callbacks sharing a millisecond retain the stability window; only backwards time or a gap above 150 ms resets it. Missing tracking, sample gaps and movement reject the contact. Closing/backgrounding the setup, leaving Room, disconnecting, or a two-minute timeout stops capture. These thresholds are provisional pending physical-contact validation; stable tracking does not itself prove that the fingertip is touching the display.

Four contacts are checked for consistent rectangle geometry and fitted with the transmitted marker insets, then converted into the existing monitor anchor's parent space using public Entity conversion APIs. The model and Blender objects are not repositioned by calibration. Diagnostics log at most twenty aggregate samples per attempt (provider/hand availability, pinch-strength buckets, sample count/span and fingertip spread), plus contact count and stop status; raw joint coordinates are ephemeral. This path fits a **flat monitor proxy**, including for a curved screen's four corner contacts; it does not measure curvature or reconstruct the curved surface.

## Link Blender's view

Enable **Allow PICO viewport control** in Blender, then **Link Blender viewport** in the PICO toolbox. Both switches default off.

### Room: head-tracked monitor camera

1. Connect to Blender and open Room. Align the monitor, accept the world alignment or **Lock alignment** after manual placement. Keep Blender's viewport size/layout unchanged after measuring it.
2. Enable **Allow PICO viewport control** in Blender's PICO Bridge panel.
3. Enable **Link Blender viewport** in the PICO toolbox. On first use, the model is staged behind the monitor. Blender creates a temporary **PICO Bridge Camera** for the selected viewport; the scene's production camera stays unchanged.
4. Move your head sideways or closer to the monitor. The view shifts and its field of view changes so its rays pass through the calibrated screen rectangle. Pinch/drag, rotate or scale the model in PICO: Blender compensates through the camera, without changing authored object transforms. Timeline synchronization continues.
5. With **Hide Blender source after extraction** enabled, the Blender camera clips foreground geometry at the monitor plane as the native model emerges; the existing source visibility lease hides it completely after extraction. **Reset take** returns the model behind the monitor. Disable the link to restore Blender's original viewport and render dimensions.

This is an asymmetric, screen-aligned perspective driven by the public tracked HMD position. Head orientation changes the tracked viewpoint but does not rotate the physical monitor. The rendering headset's optical FOV and VST camera intrinsics are different quantities; copying either as the desktop lens would not produce correct screen-window perspective. The current public Kotlin SDK path does not provide a verified per-render-eye projection getter. We do not claim an exact clone of a left/right rendering camera.

The temporary camera is viewport-local. While linked, render resolution and pixel aspect temporarily match the selected viewport for a full-frame camera image; stopping, disconnecting, loss of the one-second stream lease, opt-out, or a model revision change restores them. Resizing the target viewport stops the link; recalibrate before resuming. In Room, geometry revisions preserve the current fit scale, fit offset, inspection pose, explosion amount and staged Reset take pose. New bounds do not recenter surviving geometry. An active Room camera link pauses during replacement and rebinds after the matching model is ready; explicit opt-out is respected. Preview keeps its bounded auto-fit behavior. The native sender uses an 11 ms camera cadence target, with latest-wins backpressure and one active request. Blender applies fresh poses on a separate 8 ms timer while scene state/export checks remain at 20 Hz. HTTP connections are reused and small-packet buffering is disabled on the server. These are scheduling targets; actual rates depend on HMD delivery, transport and viewport rendering. Independent displays are not frame-locked.

A flat monitor with matching viewport/display proportions is the geometric target. A curved monitor currently uses its chord as a flat projection window, while native occlusion retains the curved surface. Exact curved-screen correspondence requires a nonlinear image warp. A single monitor also cannot match both stereo eyes away from the screen plane. Renderer lighting/shading and native per-part explosion offsets are not mirrored by this rigid camera transform. Physical visual continuity and gesture comfort still require headset validation.

### Preview: orbit, pan and zoom

Preview retains the earlier bounded gesture commands and follows Blender's reported pivot, orientation and distance. CAMERA perspective is excluded. Disabling restores the native inspection pose; source hiding is suspended in this mode. It is not a calibrated physical-screen projection.

## Gesture continuity

Adding or releasing a pinched hand rebases the transform gesture instead of moving the model to a new pointer centroid. The app also rejects nonfinite input and single-update translations over 25 cm, then accepts subsequent valid motion normally. This guard applies to model manipulation and viewport handles. Scale and Explode keep their existing two-hand behavior. The user confirmed on the real PICO that both modes remain stable when adding and releasing the second hand. If a tracked-camera stream fails, the app requests Blender source restoration and stops renewing its hiding lease; re-enable the viewport link after resolving the connection/tracking issue.
